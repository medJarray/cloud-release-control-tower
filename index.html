  2. 02

Supervision

Ce qui casse, où, et pourquoi.

Pods en échec, workloads dégradés, services ECS qui reculent : le cockpit range tout du plus urgent au plus calme, avec la raison donnée par Kubernetes ou par ECS. Un clic et tu es dans les logs.

Kubernetes en profondeur

Namespaces, workloads, replicasets, pods, services et events, avec la version déployée et la raison de chaque redémarrage.

ECS par profil et région

Clusters, services, rollouts et rollbacks, tâches arrêtées dans l'heure avec le code de sortie de chaque conteneur.

Logs en direct

Pods, workloads, services ECS via CloudWatch. Le run précédent d'un conteneur qui redémarre dit pourquoi il est tombé.

Droits restreints, vue honnête

Sans droit de lister le cluster, l'app lit namespace par namespace et dit ce qu'elle n'a pas pu voir.

Se connecter

Les commandes à lancer sur ton poste.

Control Tower n'a pas d'écran de connexion pour Google Cloud ou AWS : tu ouvres ta session dans ton terminal, il la réutilise. La règle est simple : si kubectl et aws répondent dans ton terminal, Control Tower voit la même chose.

Pas à l'aise avec le terminal ? Réglages → Connexions → Préparer ce poste installe gcloud et la CLI AWS et lance ces mêmes commandes, chacune après ton accord.

GKE

Un cluster Google Cloud

Ta session gcloud ouvre le cluster. Control Tower lance gke-gcloud-auth-plugin, comme kubectl, et reçoit un token de courte durée.

# 1. Ouvre ta session Google Cloud
$gcloud auth login
# 2. Le plugin d'authentification, une seule fois
$gcloud components install gke-gcloud-auth-plugin
# 3. Ajoute le cluster à ton kubeconfig
$gcloud container clusters get-credentials <cluster> --region <région> --project <projet>
# 4. Vérifie que ça répond
$kubectl get pods -n <namespace>

Dans l'app : Réglages → Clusters et profils, coche le contexte.

EKS

Un cluster Amazon EKS

Ta session AWS SSO ouvre le cluster. Control Tower lance aws eks get-token avec ton profil, comme kubectl.

# 1. Crée ton profil SSO, une seule fois
$aws configure sso
# 2. Ouvre ta session
$aws sso login --profile <profil>
# 3. Ajoute le cluster à ton kubeconfig
$aws eks update-kubeconfig --name <cluster> --region <région> --profile <profil>
# 4. Vérifie que ça répond
$kubectl get pods -n <namespace>

Dans l'app : Réglages → Clusters et profils, coche le contexte.

ECS

AWS ECS et CloudWatch

Control Tower lit ECS avec un profil de ~/.aws/config, SSO compris. Il t'affiche le compte et le rôle utilisés.

# 1. Ouvre ta session
$aws sso login --profile <profil>
# 2. Vérifie le compte et le rôle
$aws sts get-caller-identity --profile <profil>
# 3. Vérifie que ECS répond
$aws ecs list-clusters --profile <profil> --region <région>

Dans l'app : Réglages → Clusters et profils, ajoute le profil AWS et sa région.

K8s

Tout autre cluster

Tout contexte de ton kubeconfig marche, kubelogin compris. L'app lit KUBECONFIG, sinon ~/.kube/config.

# Tes contextes
$kubectl config get-contexts
# Si ça répond, Control Tower le lit aussi
$kubectl --context <contexte> get pods -n <namespace>
# Tes droits dans un namespace
$kubectl auth can-i list pods -n <namespace>

Dans l'app : si tu ne peux pas lister les namespaces, indique les tiens dans Réglages → Clusters et profils.

Tokens

GitLab et Jira

Édition complète

Ici, pas de commande : un token que tu colles une fois dans l'app, qui le garde sur ton poste.

GitLab
Saisis l'adresse de ton instance, puis « Créer un token » : GitLab s'ouvre avec le scope read_api déjà coché. Colle le token.
Jira Cloud
Ton e-mail et un API token, créé sur id.atlassian.com → Sécurité → API tokens.
Jira Data Center
Un token personnel, ou « Ouvrir la fenêtre de connexion » pour le SSO de ton entreprise : la session est gardée sur ton poste, comme les tokens.

Sans GitLab : « Superviser mes clusters sans GitLab » ouvre directement le cockpit.

IA

Copilot et MCP

Édition complète

Control Tower utilise le CLI GitHub Copilot de ton poste, avec ton compte. Il ne voit jamais son token.

# 1. Installe le CLI Copilot : macOS, Windows ou npm
$brew install --cask copilot-cli
$winget install GitHub.Copilot
$npm install -g @github/copilot
# 2. Connecte-toi
$copilot login
# VS Code ou Copilot CLI : les lignes à ajouter
$crct-mcp config

Dans l'app : Réglages → Copilot → « Vérifier à nouveau ».

Sur Windows, ce sont les mêmes commandes dans PowerShell. Remplace les valeurs <entre chevrons> par les tiennes.

Session expirée ? La même commande, puis « Rafraîchir »

L'app ne te redemande jamais un mot de passe : elle affiche un code et la commande à relancer dans ton terminal.

aws_sso_expired
La session AWS SSO a expiré.
aws sso login --profile <profil>
k8s_unauthorized
La session du cluster a expiré.
gcloud auth login ou aws sso login
k8s_auth_plugin
Le plugin du kubeconfig est introuvable.
Installe-le et vérifie qu'il est dans ton PATH.
k8s_forbidden · aws_access_denied
Tes droits refusent cette lecture.
Rien à contourner : demande le droit si tu en as besoin.
k8s_network · aws_network
Le cluster ou AWS est injoignable.
Vérifie ton VPN, ton proxy ou ton réseau.

Secrets et session locale

Control Tower emprunte ta session. Tes secrets restent sur ton poste.

Il y a deux sortes d'accès, et aucune ne quitte ton poste : les sessions que tu ouvres dans ton terminal, que l'app ne stocke jamais, et les tokens que tu colles, que l'app garde dans un fichier à elle.

Kubernetes et AWS

La session de ton poste

Rien à saisir dans l'app, rien de stocké par l'app.

  1. 1Tu ouvres ta session dans ton terminal avec gcloud auth login ou aws sso login.
  2. 2gcloud et la CLI AWS gardent cette session dans leurs propres dossiers. Control Tower n'y touche pas.
  3. 3À chaque lecture, l'app demande un accès court : le plugin de ton kubeconfig pour un cluster, ton profil pour AWS.
  4. 4Cet accès reste en mémoire, le temps que l'app tourne. Il n'est écrit ni dans sa base, ni dans ses réglages, ni dans un log.

GitLab et Jira

Les tokens que tu colles

Saisis une fois, rangés dans un fichier de l'app.

  1. 1Tu colles ton token dans l'app, une seule fois.
  2. 2Il est écrit dans crct-secrets.json, dans le dossier de données de l'app, lisible par ton compte seulement (droits 600 sur macOS). Pas de trousseau du système : c'est un fichier, comme ~/.aws/credentials.
  3. 3Le cœur de l'app le lit au moment de l'appel et ne l'envoie qu'à GitLab ou à Jira. L'interface ne le revoit jamais.
  4. 4« Déconnecter » l'efface du fichier. Tu peux aussi le révoquer côté GitLab ou Jira.

Serveur Control Tower

Il n'existe pas. Pas de compte à créer, rien à synchroniser, aucun de tes secrets ne nous parvient.

Ce que Control Tower ne fait jamais

  • Te demander ton mot de passe Google ou AWS.
  • Écrire un secret dans sa base, ses réglages ou un log.
  • Envoyer un token ailleurs que vers le service qui l'a émis.
  • Laisser passer un secret dans une ligne de log : bearer, basic, password=, clés AWS, JWT et tokens GitLab ou GitHub sont masqués.
  • Appeler un serveur à nous : ni télémétrie, ni vérification de mise à jour.

Sur ton poste, et nulle part ailleurs

L'environnement de ta session
Sur macOS, l'app reprend l'environnement de ton shell de login, PATH, KUBECONFIG, AWS_* et proxys : elle trouve gcloud, aws et kubelogin comme ton terminal. Sur Windows, ce sont les variables de ta session.
Une base locale, sans secret
Cache GitLab, réglages et journal dans ~/Library/Application Support/com.alphasolutionsit.crct sur macOS, %APPDATA%\com.alphasolutionsit.crct sur Windows. Les tokens sont à côté, dans crct-secrets.json.
Des connexions directes
De ton poste vers l'API Kubernetes, AWS, GitLab et Jira, par ton réseau et ton VPN. Aucun intermédiaire.
Une seule sortie, si tu la choisis
Avec Copilot, ta question et ce que les outils ont lu partent vers GitHub Copilot, via ton compte, secrets masqués. Sans Copilot, rien ne part.

Lecture seule

Rien n'est modifié, et des tests le prouvent.

Les garde-fous vivent dans le code qui envoie les requêtes, pas dans une option qu'on oublie de cocher.

Bloqué avant l'envoi

Kubernetes : GET uniquement. AWS : List, Describe, Get, Filter et StartLiveTail. GitLab : GET et HEAD. Jira : GET et la recherche.

Vérifié à chaque build

Des tests le prouvent : un DELETE ou un UpdateService n'atteint jamais le serveur, un utilisateur restreint ne voit que ses namespaces.

Tes droits, sans détour

RBAC et IAM s'appliquent tels quels, pour l'app comme pour Copilot. Un rôle de lecture suffit : aucun droit d'écriture n'est demandé.

Journal des actions sensibles

Connexions, réglages cloud, logs ouverts, chaque outil appelé par Copilot ou un client MCP, avec son issue. Il reste sur ton poste.

Questions fréquentes

Avant d'installer

Dois-je donner mon mot de passe Google ou AWS à l'app ?

Non, jamais. Tu ouvres ta session dans ton terminal avec gcloud ou aws, et l'app réutilise cette session par ton kubeconfig et tes profils.

Mes données passent-elles par un serveur à vous ?

Non, il n'y en a pas. L'app parle directement à tes clusters, à AWS, à GitLab et à Jira depuis ton poste. Pas de compte, pas de télémétrie.

Où sont mes tokens GitLab et Jira ?

L'édition Cloud n'en garde aucun. Dans l'édition complète, ils sont dans crct-secrets.json, dans le dossier de données de l'app, lisible par ton compte seulement. C'est un fichier en clair, comme ~/.aws/credentials : protège ta session comme tu protèges celle-là. « Déconnecter » l'efface.

Que se passe-t-il quand ma session expire ?

L'app affiche le code de l'erreur et la commande à relancer, par exemple aws sso login. Tu la lances dans ton terminal, puis « Rafraîchir ».

Control Tower peut-il modifier mes clusters ?

Non. L'app n'a aucune action d'écriture, et ses clients Kubernetes et AWS refusent toute requête qui ne lit pas avant même qu'elle parte.

Faut-il installer quelque chose dans les clusters ?

Non, ni agent ni opérateur. L'app lit l'API Kubernetes avec ton kubeconfig, comme kubectl, et AWS avec tes profils.

Et quand j'utilise Copilot ?

Copilot sera dans l'édition complète, bientôt disponible. Ta question et ce que les outils lisent partent vers GitHub Copilot, via ton compte, secrets masqués. Jamais tes tokens ni tes fichiers. Sans Copilot, rien ne part.

Quelle édition choisir ?

Aujourd'hui, l'édition Cloud : elle surveille tes clusters et tes services, sans GitLab, Jira ni Copilot, et ne garde aucun jeton. L'édition complète, bientôt disponible, y ajoutera tes releases et tes stories ; tes réglages resteront quand tu passeras de l'une à l'autre.

GitLab est-il obligatoire ?

Non. L'édition Cloud s'en passe complètement. Dans l'édition complète aussi, le cockpit, les logs et les versions déployées marchent sans GitLab ; le contenu de chaque tag et la comparaison aux releases GitLab l'attendent.

Au premier lancement, mon Mac bloque l'app ?

Tant que l'app n'est pas notarisée par Apple, macOS demande une confirmation, une seule fois : lance l'app, puis Réglages Système → Confidentialité et sécurité → « Ouvrir quand même ».
